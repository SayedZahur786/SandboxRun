# Adversarial test methodology

SandboxRun's 40 named checks test the configured capability boundary, resource limits, and per-run isolation. They are regression evidence, not a proof against all sandbox escapes or an external security audit. `escape-results.json` is generated by the integration test; the test never marks an interpreter crash, syntax error, or unrelated initialization failure as a successful denial.

Every counted case must print its unique start marker before attempting the operation. Capability cases must then report an explicit expected denial (errno, null/error result, or a specifically absent API). Resource cases must return the expected limit status. Every case checks that captured output stays within its byte budget, a disposable host file remains unchanged, no new host file appears in the fixture directory, and neither a host-only environment value nor the host file's contents appear in output.

The host-only environment value is supplied to an isolated test process. No real credential or user document is used. Python and JavaScript positive controls run before and after the adversarial cases. Two seeded globals must disappear in subsequent independent executions.

The suite separates filesystem and descriptor denials, process and network denials, explicitly absent language capabilities, blocking host-call denials, resource limits, and cross-run isolation. Missing Node APIs are reported as missing capabilities, not as successful attempts to exploit a Node runtime.

Execution duration must stay below the requested wall budget plus a 250 ms scheduling allowance. Blocking-sleep checks must complete within 250 ms despite requesting a one-second sleep. This allowance accounts for test-host scheduling and does not enlarge the production requested limit. An additional invalid-UTF-8 output regression verifies that replacement characters cannot inflate a serialized output stream past its byte cap; it is outside the count of 40.

Run the integration test with:

```sh
cargo test --release --test escape_suite
```

`escape_suite` starts its ignored helper explicitly with a seeded environment. The helper's ignored status in the outer test listing is intentional; its execution and assertions are required for the wrapper test to pass. The machine-readable report includes source hashes, host architecture, start-marker evidence, specific statuses, actual timings, and fuel consumption. The suite's startup timing is local runtime initialization, not a hosted cold-start measurement.

The bundled CPython standard library is a read-only virtual filesystem inside its WASM artifact. It does not grant a host-directory preopen. Tests verify both forbidden host access and failed writes to this embedded library.

Compatibility finding: importing Python `subprocess` reaches the denied WASI polling host call before `subprocess.run` can be invoked. That observation is not counted as a subprocess escape attempt. The module is unsupported in this capability profile. Blocking sleeps are tested directly and terminate with `capability_denied`; other Python standard-library modules that require polling or unavailable host services may also be unsupported.
